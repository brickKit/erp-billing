# erp/billing 的设计

本页写这个组件为什么这样设计：术语、拥有的数据、状态、规则要点、命令与事件、依赖、实现状态与未决问题。写给要修改它的人与 AI。怎样使用、部署与配置在 `BRICKKIT.md`；代码在哪、怎样构建与测试在 `AGENTS.md`。从草拟到正式化每一步的顺序、失败与恢复在 [flows/billing.md](flows/billing.md)。

跨组件的规则在装配项目：认领模式、可出账台账、出账组件本地的草稿与正式化的顺序在协议 05（本组件是“出账”用法的使用方），单号与金额在协议 14，打印在协议 10，关账的参与在协议 06；端到端的位置见装配项目的业务流程“订单到收款”。

## 边界

向客户开具账单（商业发票）：从来源认领可出账额度，按法人连续编号并正式化，发布“已出账”事实。

| 不在这里 | 归谁 |
| --- | --- |
| 可出账额度的裁决 | 来源：`erp/sales`（订单行）、`prj/project`（里程碑）、`erp/contract`（订阅期） |
| 应收、核销 | `erp/finance`（接收“已出账”形成应收） |
| 信用占用的转换 | `erp/credit`（接收“已出账”） |
| 税额的计算 | `erp/tax`（远期；缺时用来源行的人工税率） |
| 电子发票的报送 | `integration/einvoice-<地区>` |
| PDF 的渲染 | `infra/print`（本组件提供数据与模板版本） |

## 术语

| 业务叫法 | 定义 | 代码标识符 |
| --- | --- | --- |
| 账单与明细 | 一个法人给一个客户、一种币种的账单；明细引用来源行 | `invoice`、`invoice_line` |
| 来源 | 账单行引用的可出账额度：本版只有销售订单行 | `source_kind`：`sales_order`；`source_line_id` |
| 认领 | 本组件对来源额度的认领，认领身份等于账单身份（一张账单一个认领，覆盖多行） | `claim_id` |
| 草稿、已确认、已编号、已作废 | 账单在本组件内的状态（协议 05 的“出账组件本地的草稿”） | `status`：`draft`、`confirmed`、`issued`、`void` |
| 正式化回报 | 已编号的账单向来源发正式化，直到来源确认 | `formalization`：`pending`、`done` |
| 账单号 | 按法人、按年连续，编号事务中分配，作废不收回 | `number` |
| 已出账 | 账单编号时发布的不可遗漏的增量事实，供财务与信用 | `erp.invoice.issued.v1` |
| 更正（冲回）、补差、红字 | 以后（协议 05） | — |
| 打印快照 | 账单第一次渲染时记下的模板版本与视图模型（已格式化的打印数据）；之后每次渲染都用它，不重新取当前模板、不重新格式化 | `print_template`、`print_version`、`print_data` |
| 副本 | 第二次及以后渲染的 PDF 标为副本 | `print_count` |

| `invoice_line` | 明细：来源行、产品快照、数量与单位、单价、金额、税率、税额 | 随账单 |

## 账单的状态

照协议 05 的“出账组件本地的草稿”，按行序第一条命中：

| 当前状态 | 事件 | 结果状态 | 动作 |
| --- | --- | --- | --- |
| （无） | 草拟（认领成功） | `draft` | — |
| （无） | 草拟（认领被拒） | — | 不建账单，回答来源的原因 |
| `draft` | 修改数量（只减不增） | `draft` | 认领不变；正式化时按实际数量 |
| `draft` | 用户作废 | `void` | 本地提交后向来源释放认领 |
| `draft` | 来源确认成功 | `confirmed` | — |
| `draft` | 来源拒绝确认（认领已到期） | `void` | 不编号 |
| `confirmed` | 编号事务 | `issued` | 正式账单号、“已出账”进发件表；之后向来源发正式化 |
| `confirmed` | 用户作废 | `void` | 本地提交后才向来源释放认领 |
| `void` | 编号事务 | `void` | 编号失败 |
| `issued` | 正式化未确认 | `issued` | 恢复工作项重发正式化，直到来源确认 |

## 规则要点

- 认领由来源裁决，同一来源额度不被重复出账；本组件只认领、不自己算余额。
- 编号之前认领已确认、不会到期；不经本地作废就不释放已确认的认领（BL25）。
- 编号：`db.NextNumber`（序列行在 SDK 的表 `doc_series`）在编号事务中取号（幂等认领之后），按法人、按开票日期所在的年（法人时区）连续；格式 `INV-<法人代码>-<年>-<六位序号>`，本版固定。
- 占号：只有进入 `issued` 才有号；草稿与已确认的账单作废都不占号；已开具的不能作废，只能更正（以后），号永不收回（协议 14）。
- 开票日期是编号事务的业务日期（法人时区的今天）。
- 正式化之后不修改；更正以新单据表达（以后）。
- 金额：账单行金额等于认领的金额维；税额 = 行金额 × 来源行的税率，按行舍入（与销售声明一致）；合计不另行舍入。外币账单沿用订单的汇率快照。
- 客户是来自订单的历史引用（协议 07），开票不重新问客户资格；法人在编号前取证（`mdm/org` 来源读取，必须 `active`）。
- 打印：只有 `issued` 的账单能取 PDF。第一次取时，按账单的数据格式化视图模型（日期、金额、大写按账单的语言与法人时区），连同打印组件答复的模板版本记成打印快照；之后每次都把同一个版本与同一份视图模型交给打印，所以模板改了、格式化代码改了，旧账单重打的内容都不变（协议 10 的“正式单据记录模板版本”）。打印次数在账单行锁下加一，第二次起在视图模型之外另传“副本”标记；两个人同时取 PDF，各得一个不同的次数。第一次渲染失败不记快照、不计次数。

## 事件

流 `erp.billing`：

- 已出账（`erp.invoice.issued.v1`）：不可遗漏的增量事实（协议 05 的共同规则），事实身份是账单身份；带法人、客户、币种、金额、税额、来源（订单与行）与信用分支所需的订单身份。在编号事务中写入发件表。
- 账单 `erp.invoice.changed.v1`：可覆盖的完整状态事件（也是 `InvoiceService.Read` 的数据）。
- 以后：更正、预收抵扣行、关账的“已封存”“已解封”。

## 实现状态

实验第 7 步：从销售订单草拟（认领）、修改与作废草稿、开具（确认、编号、正式化及其恢复）、账单查询、已出账与账单状态事件、取 PDF（按需渲染，不保存）。答“能力不支持”的：更正与补差、红字、预收抵扣、电子发票、按序号补取（协议 06）、项目与合同来源。

PDF 本版不保存，这是协议 10、协议 12 的“正式单据的输出保存为附件”的本版例外：附件组件不在本步。在那之前，打印快照（模板版本与视图模型）代替附件保证重打一致，渲染的确定性由打印组件保证；附件组件上线后，第一次渲染的输出存为附件，重打取附件、标副本。

## 部署与替换

中负载、月末高峰；适合外壳。同一法人同一年的编号串行（连续序列的吞吐上限）；超出时按协议 14 由业务选择允许缺号或期末批量编号，本版不需要。出账规则（合并出账、拆分与汇总）是替换点。适用协议 01、02、05、06、07、10、13、14、16、安全 01–09。

## 未决问题

- 一张账单合并多张订单（合并出账）：本版一张账单只来自一张订单。
- 恢复工作项遇到 `confirmed` 但没编号的账单（编号前崩溃）：协议 05 的状态表允许两种走向（作废后释放认领，或完成编号）；本版选完成编号（用户的意图是开具），超过一天仍未编号的告警，不自动作废。
