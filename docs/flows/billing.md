# 出账的顺序

从订单草拟到正式化，每一步做什么、调谁、失败或结果未知时怎样。认领的守卫与状态在协议 05 的认领模式，账单本地的状态在 [design.md](../design.md#账单的状态)；测试按协议 05 的 BL 编号命名。

## 草拟

| 步骤 | 做什么 | 失败时 |
| --- | --- | --- |
| 1 | 幂等认领（`Idempotency-Key`） | 同键同请求返回原账单 |
| 2 | 读订单（销售的系统读取）与可出账台账；行与数量缺省为每行剩余（`billable − claimed − billed`，两维） | 没有剩余：拒绝 |
| 3 | 向销售认领（认领身份 = 新的账单身份） | 拒绝：不建账单，回答原因（BL01）；未知：用同一身份重试（BL02），仍未知则答“依赖不可用”，留给认领的到期回收 |
| 4 | 事务：建账单 `draft`，明细与快照 | — |

第 3 步成功、第 4 步之前崩溃：来源留着一条 `pending` 认领，没有账单；认领到期后由来源回收（7 天）。用户用同一 `Idempotency-Key` 重试时，用同一账单身份再认领，来源返回原认领，接着建账单。为此第一次草拟在认领之前把账单身份与认领的行随幂等键记下（`draft_key`），重试取回同一份，不重新取剩余：自己的认领已经占了剩余，重新取会得到“没有剩余”。

## 开具

顺序：用户开具（`Idempotency-Key`）→ 向 `erp/sales` 确认认领 k。已到期时来源拒绝，事务把 `draft` 转为 `void`（不编号），结束；已确认时事务把 `draft` 转为 `confirmed` → 事务外向 `mdm/org` 读法人取证 → 编号事务：锁账单，仍是 `confirmed` 才 `NextNumber`，转 `issued`，发件表写“已出账” → 向 `erp/sales` 按实际数量正式化 k，来源答“已出账”后，事务记正式化回报 `done`。

| 步骤 | 失败或结果未知 |
| --- | --- |
| 确认认领 | 未知：用同一身份重试（BL24）；拒绝：账单作废（BL05、BL26） |
| 法人取证 | 法人不是 `active`：停在 `confirmed`，回答原因；用户可以作废（释放认领）或等法人恢复后再开具 |
| 编号事务 | 账单已被作废：编号失败，回答“已作废”（BL25）。编号事务在幂等键之下（`idem.Do`），同一个键重试拿回同一个结果，不重复取号 |
| 正式化 | 未知或失败：编号事务里已排入恢复工作项（协议 01），重发直到来源确认（BL04）；用户看到的账单已是正式的 |

## 草稿的认领到期

草稿的认领在来源是 `pending`，期限是销售的 `ClaimPeriod`（7 天；本组件不续期）。到期由来源回收：销售的 `expire-claims` 工作项每分钟把过期的认领释放回可出账。本组件不订阅也不轮询到期，所以账单在本地仍是 `draft`，直到下一次操作：开具时来源拒绝确认，账单作废、不编号（BL05、BL26）；作废照常。

## 作废

| 状态 | 做什么 |
| --- | --- |
| `draft` | 事务：`void`；之后向来源释放认领（失败由工作项重发；释放是幂等的） |
| `confirmed` | 同上；先本地作废，再释放，不能反过来（BL25） |
| `issued` | 拒绝：正式账单只能更正（以后） |

## 恢复工作项

| 工作项 | 何时排入 | 做什么 |
| --- | --- | --- |
| 正式化 | 编号事务里 | 向来源正式化，直到确认；然后正式化回报 `done` |
| 释放 | 作废的事务里 | 向来源释放，直到成功 |
| 继续开具 | 确认认领后的事务里（`ContinueAfter`，一分钟之前让路给原请求） | 发现仍是 `confirmed`（开具中途崩溃）：重新取证、编号；仍不行就重试，`confirmed` 超过 `StuckAfter`（24 小时）记一条错误日志告警，不自动作废：已确认的认领不会到期，要释放只能由人作废 |
